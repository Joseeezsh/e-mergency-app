Mobile Application Technology — Final Case Study

E-mergency App (Electronic Emergency)

Zero-Account Geolocation-Assisted Emergency Reporting & Dispatch Monitor Mobile Application

Package ID: com.emergency.app
Stack: Ionic 9 · Angular 22 · Capacitor 8 · Leaflet
Group Members: Gregorio, Maricar F. · Marcelo, Ana Leah D. · Olinares III, Jose A. · Villamia, Beatriz D.

1. Problem Statement & Proposed Solution

Problem

During sudden medical, fire, vehicular, or personal security emergencies, individuals face two critical barriers when using conventional emergency or incident-reporting apps: (1) mandatory account registration or login flows delay help when seconds matter, and (2) panicked callers frequently struggle to describe their exact street address or landmarks to responders. Conversely, single-tap SOS buttons without safeguards risk triggering accidental calls to emergency hotlines such as 911.

Solution: E-mergency App

E-mergency App removes authentication friction completely by launching directly into the SOS screen, automatically acquiring GPS coordinates via Capacitor Geolocation, rendering the caller's live position and accuracy radius on an interactive Leaflet map, and resolving a human-readable street address using OpenStreetMap Nominatim. To prevent unintended emergency calls, pressing SOS — CALL 911 initiates a cancelable countdown guard (default 5s, configurable to 3s/5s/10s) accompanied by haptic pulses. A default-enabled Safe Test Mode allows full end-to-end demonstrations and classroom testing without dialing real 911.

2. Core Features & User Experience

User SOS Tab (/tabs/sos)

  • Zero-Login Entry: Opens straight to emergency controls.
  • Live GPS & Leaflet Map: Displays pulsing pin, accuracy circle, coordinates, and resolved street address.
  • Category & Note: Quick chips (Medical, Fire, Accident, Security, General) plus optional landmark note.
  • Cancelable Countdown Guard: Haptic ticks + prominent CANCEL SOS button.
  • Emergency Output Card: Copyable summary & direct OpenStreetMap link.

Admin Monitor & Settings

  • Admin Monitor (/tabs/admin): Live badge count of Active alerts; filter by All, Active, Ack, Done.
  • Map Inspector: Shared EmergencyMapComponent pins any selected alert for dispatcher verification.
  • Lifecycle Controls: Mark alerts Acknowledged or Resolved (with timestamp).
  • Settings (/tabs/settings): Safe Test Mode toggle, countdown duration selector (3s/5s/10s), and log clearing.

3. Technical Implementation & Architecture

The application is structured using Angular 22 standalone components and reactive Signals (signal, computed) inside Ionic 9 tabs, packaged for Android via Capacitor 8.

Layer / File Responsibility & Key APIs
src/app/models/emergency.model.ts Strongly typed interfaces for EmergencyAlert, GeoLocationFix, AppSettings, EmergencyCategory, and AlertStatus.
src/app/services/location.service.ts Checks and requests native Android location permissions via @capacitor/geolocation, returning latitude, longitude, and meter accuracy.
src/app/services/geocoding.service.ts Uses Angular HttpClient (GET) against OpenStreetMap Nominatim (format=jsonv2) with a 6s timeout and graceful offline coordinate fallback.
src/app/services/emergency-store.service.ts Persists alerts and settings locally using @capacitor/preferences and exposes read-only Signals (alerts, settings, activeCount).
src/app/services/emergency-dispatch.service.ts Coordinates @capacitor/haptics pulses, alert persistence, @capacitor/local-notifications Admin alerts, and Safe Test Mode / tel:911 dialer handoff.
src/app/components/emergency-map/ Shared Leaflet component rendering OpenStreetMap tiles, a pulsing CSS marker (.emergency-pin-dot), accuracy circle, and Ionic tab resize handling.
android/app/src/main/AndroidManifest.xml Declares INTERNET, ACCESS_COARSE_LOCATION, ACCESS_FINE_LOCATION, POST_NOTIFICATIONS, and VIBRATE.

Architectural Limitation & Future Improvement:
To keep the case study self-contained with zero backend credentials, alerts are stored locally on-device via @capacitor/preferences. Consequently, the SOS sender and Admin Monitor operate on the same device rather than across separate caller and responder devices. In a production deployment, EmergencyStoreService and EmergencyDispatchService can be extended to push alerts to a cloud database (e.g., Firebase Firestore or Supabase) with Firebase Cloud Messaging (FCM) push notifications while preserving the zero-account caller workflow.

5. End-to-End Dispatch Flow & Android Packaging

At runtime, the application follows a deterministic, fault-tolerant sequence from launch to responder review:

  • 1. Immediate Launch: tabs.routes.ts routes directly to /tabs/sos with no authentication screen.
  • 2. GPS & Address Resolution: LocationService requests Android location permissions and acquires coordinates; GeocodingService fetches street details via Angular HttpClient (GET) or falls back cleanly when offline.
  • 3. Guarded Dispatch: SosPage runs a cancelable countdown (3s/5s/10s) with Haptics.impact ticks. Upon completion, EmergencyDispatchService saves the alert, triggers a local notification, and honors Safe Test Mode before opening tel:911.
  • 4. Android Build Pipeline: Web assets compiled via pnpm run build are synced into android/ with pnpm exec cap sync android and packaged into an installable .apk in Android Studio (Build > Build APK(s)).
